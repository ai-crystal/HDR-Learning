# 第 10 章 位深、编码与色度采样：10bit、4:2:0 与 ICtCp

前面几章反复出现几个数字：10bit、4:2:0、YCbCr、ICtCp……它们听上去像黑话，其实都在回答同一个问题——**HDR 画面的数据量太大了，我们怎么用有限的精度和带宽把它装下、又尽量不让人看出破绽？**这一章我们就来拆解这些"装箱技巧"。读完你会明白：为什么 HDR 非要 10bit 起步、为什么视频总爱"偷懒"少存颜色、以及 8bit+FRC 到底算不算 10bit。

## 10.1 位深与量化：楼梯有多少级

先说**位深（bit depth）**，也叫**色深**。

数字世界里，亮度不是连续的，而是被切成一段段**离散的台阶**。这个"切台阶"的过程叫**量化（quantization）**。**位深就是台阶的级数**：

- **8bit**：每通道 2⁸ = **256** 级台阶。
- **10bit**：每通道 2¹⁰ = **1024** 级台阶。
- **12bit**：每通道 2¹² = **4096** 级台阶。

> **类比**：位深像楼梯的级数。8bit 是一段只有 256 级的楼梯，每级都很"陡"；10bit 是 1024 级，台阶更细，走上去更顺滑。你站在哪一级，就是画面显示的亮度。

注意：位深是**每个通道**的级数。一个彩色像素由红、绿、蓝三个通道组成，所以：

| 位深 | 单通道级数 | 理论可表达颜色数（RGB 三通道相乘） |
|---|---|---|
| 8bit | 256 | 约 1677 万色 |
| 10bit | 1024 | 约 **10.7 亿**色 |
| 12bit | 4096 | 约 **687 亿**色 |

从 8bit 到 10bit，颜色数从"千万级"跳到"十亿级"，差了 64 倍。

## 10.2 色带（banding）是怎么来的

台阶不够细，就会露馅。当画面里出现**缓慢、平滑的亮度或颜色渐变**时（比如黄昏天空、雾、暗场景的墙面），如果台阶太粗，人眼就会看到一条条明显的条带，这就是**色带（banding）**，也叫"等高线状条纹"。

```text
理想渐变（连续）          8bit 量化后（台阶太粗）
  ░▒▓█                    ░ ▒ ▓ █   ← 看到一条条硬边
 平滑过渡                  ▒▒▒▓▓▓    ← 这就是 banding
```

**为什么 HDR 特别容易出色带？** 关键在 PQ 曲线（见第 7 章）。PQ 是绝对式编码，把大量码值分配给了很暗的区域——暗部的曲线非常陡。用 8bit 那 256 级台阶去装 PQ 暗部，**每一级之间跨度太大**，暗场景立刻糊出条纹。这就是"HDR 必须 10bit 起步"的根本原因：**不是为了让颜色更艳，而是为了不让 PQ 的暗部露馅。**

## 10.3 8bit vs 10bit vs 12bit：实际差别

| 位深 | 台阶数 | 主要用途与差别 |
|---|---|---|
| **8bit** | 256 | SDR 时代的标准。用来装 HDR/PQ 时，暗部极易出现色带 |
| **10bit** | 1024 | HDR10 / HDR10+ 的**起步配置**，也是绝大多数消费级 HDR 屏的实际水平 |
| **12bit** | 4096 | 母版制作、专业链路、Dolby Vision 可支持。消费级屏幕**几乎见不到"真 12bit"面板** |

要点：

- **10bit 是 HDR 的"及格线"**，8bit 往往是"看着像 HDR，暗部却是条纹"。
- **12bit 更多出现在制作端和处理链路**（母版、编码），不代表你家里的屏幕就是 12bit 的。别把"内容支持 12bit"误读成"屏幕是 12bit"。
- 很多片源在编码、传输环节会做取舍（压到 10bit、做色度采样），最终到达屏幕的未必是"全程"高精度。

## 10.4 抖动（dithering）与 FRC：8bit+FRC 不是真 10bit

面板不够位深，厂商又有办法"补救"，这就是**抖动（dithering）**。

**抖动的思路**：既然我只有 256 级台阶，那我可以通过**快速地在相邻两级之间来回切换**，让人眼"平均"看成一个中间值。就像只有黑白两个笔画不出灰色？那就靠"点状交替"的疏密来假装灰色——这是印刷界的老把戏。

**FRC（Frame Rate Control，帧率控制）**是抖动在时间维度上的常见实现：**在连续几帧里轮流显示相邻的两个色阶**，利用人眼的视觉暂留"骗"出一个中间色。

于是就有了市场上常见的宣传：

> "**8bit+FRC = 10bit**"。

**这里必须划重点：8bit+FRC 不是真 10bit。**

| | 真 10bit 面板 | 8bit+FRC |
|---|---|---|
| 原生台阶 | 1024 级 | 256 级 |
| 中间色怎么来 | **真实存在** | **靠时间上交替"骗"出来** |
| 静态画面 | 干净稳定 | 可能出现**轻微闪烁或噪点** |
| 快速运动画面 | 正常 | 更容易露馅 |
| 本质 | 真精度 | 伪精度（视觉平均） |

日常观看下，好的 8bit+FRC 效果已经不错；但在**暗场、静态色块、渐变测试图**下，它和真 10bit 的差距就可能看得出来。所以看参数时：**"8bit+FRC"要当成"介于 8bit 和 10bit 之间"，而不是"10bit"。**

## 10.5 色度采样：4:4:4 / 4:2:2 / 4:2:0

解决了"精度"，还有"数据量"要省。这就是**色度采样（chroma subsampling）**。

它的根据是人的生理特点：**人眼对亮度（明暗）非常敏感，对色度（颜色）的敏感度低得多。**所以视频数据可以"亮度存全份、颜色存少份"，肉眼几乎察觉不到。

数字写法 `4:2:0` 这类，含义是"相对亮度，色度保留多少":

| 格式 | 亮度（Y） | 色度（Cb/Cr） | 数据量（相对 4:4:4） | 典型用途 |
|---|---|---|---|---|
| **4:4:4** | 全份 | 全份 | 100% | 后期制作、文字清晰的桌面、高端游戏 |
| **4:2:2** | 全份 | **水平减半** | 约 67% | 专业视频采集、部分接口模式 |
| **4:2:0** | 全份 | **横纵都减半** | **约 50%** | 影视流媒体、蓝光、绝大多数消费内容 |


要点：

- **4:2:0 是"少存颜色"，不是"图像模糊"**。它主要影响**彩色边缘的锐利度**（比如红色文字边缘），对亮度细节没有损失。
- 因为人眼对色度不敏感，**影视内容用 4:2:0 基本看不出问题**（这也是"消费内容几乎都是 4:2:0"的原因）。
- 但对**电脑桌面、细小的彩色文字、红色字幕边缘**，4:2:0 可能让颜色发虚、边缘渗色——所以 PC 场景更倾向 4:4:4（这也和接口带宽有关，见第 14 章）。

## 10.6 RGB vs YCbCr：为什么视频爱用“亮度+色差”

上面说的"亮度存全份、颜色存少份"，前提是把颜色拆成"**亮度 + 色差**"两路来表示，这就是 **YCbCr**：

- **Y**：亮度（luminance），明暗信息。
- **Cb / Cr**：两个色差（chroma）分量，描述"偏离灰多少、往蓝或红偏多少"。

对比另一种表示法 **RGB**：直接存红、绿、蓝三个通道。

| | RGB | YCbCr |
|---|---|---|
| 分量含义 | 红、绿、蓝三个颜色通道 | 亮度 + 两个色差 |
| 能否分离亮度 | 不能（三个分量都在表达颜色） | **能**，Y 单独拎出来 |
| 能否做色度采样 | 不方便 | **天然适合**（对 Cb/Cr 降采样就行） |
| 兼容黑白 | 需转换 | 天然兼容（只看 Y 就是黑白） |
| 常见场景 | PC 图形、游戏、桌面 | 视频、影视、流媒体 |

正因为 YCbCr 能把亮度单独拎出来，才能方便地"亮度存全份、色度存少份"，也才能兼容早期的黑白显示。**这就是视频普遍用 YCbCr 的原因。**

![图 10-4　RGB → YCbCr：把亮度与色度拆开](图片/10/f4_ycbcr.png)

Y 亮度变成了黑白灰的渐变图，提取出了纯粹的“明暗信息”。无论原本是鲜艳的红色还是深蓝色，只看 Y 通道，它们都变成了灰度图。人眼对 Y 是极其敏感的，所以这个通道在编码时必须保留完整的数据，不能含糊。

Cb 色差代表“蓝-黄”方向的色彩偏移（偏离灰色的程度），如果某个像素的 Cb 是中间值，说明它是灰色的（没有蓝色或黄色倾向）；如果偏蓝，就是 Cb 值高；如果偏黄，就是 Cb 值低。Cr 色差代表“红-绿”方向的色彩偏移，如果 Cr 是中间值说明是灰的；偏向红色或绿色，Cr 的值就会发生变化。

这张图用伪彩色来展示单个数据通道（Cr）的数值大小，当 Cr 的值大于中间值（即偏正）时，代表红色多，用暖色（红/橙）来标示； 当 Cr 的值小于中间值（即偏负）时，用冷色（蓝/青）来标示。这就像我们看天气预报的热力图，数值高用红色，数值低用蓝色。这里的蓝色只代表“Cr 数值低”，并不代表真实的最终颜色是蓝色。

## 10.7 ICtCp：HDR 时代的新公式

YCbCr 很好用，但它有个老毛病：它是**为 SDR、为较窄色域设计的**。到了 HDR 时代，画面又亮又广色域，YCbCr 的"亮度 + 色差"分离就开始松动——**改变颜色有时会意外地带动亮度，"恒定亮度"的假设不再成立**，于是出现颜色偏移、映射不稳等问题。

于是 HDR 引入了新的编码方式 **ICtCp**：

- **I**：类似亮度的强度（intensity）。
- **Ct / Cp**：两个色差分量。
- 它的设计目标是**更接近"感知上恒定亮度"**：在广色域、高亮度下，色度和亮度的分离更干净、更稳定。

| | YCbCr | ICtCp |
|---|---|---|
| 设计年代/对象 | SDR、较窄色域 | **HDR、宽色域** |
| 亮度-色度分离 | 一般 | **更稳**（感知上更恒定） |
| 在位深不足时 | 易出问题 | 相对更耐压缩 |
| 典型使用者 | 绝大多数内容 | Dolby Vision 等 HDR 方案 |

要记的结论很朴素：**ICtCp 不是"新色域"，而是 HDR 时代更合适的一种"颜色拆分方式"**，让画面在又亮又艳的时候少出乱子。

## 10.8 编解码：HEVC、VP9、AV1 与"元数据随码流走"

最后，这些高精度数据要**压缩、封包、传输**，才能塞进有限带宽。这就是**编解码（codec）**的活。承载 HDR 的常见主力：

| 编解码 | 常见全称 | 特点 |
|---|---|---|
| **HEVC** | H.265 / 高效视频编码 | HDR 最主流，UHD 蓝光、多数流媒体的 HDR 都用它 |
| **VP9** | —— | Google 系，YouTube 等平台的 HDR 常用 |
| **AV1** | AOMedia Video 1 | 新一代开源编解码，压缩效率更高，HDR 支持好，正快速普及 |

关键一点：**HDR 的元数据要"随码流一起走"**。

意思是——动态元数据（HDR10+ 的场景信息、Dolby Vision 的 RPU）会**嵌在视频码流里**或与之配套传输，而不是单独一张纸。播放端解出画面时，同步解出"这一帧该怎么映射"的说明，才能让动态元数据真正起作用。

```mermaid
flowchart LR
    A["母版<br/>高精度 + 元数据"] --> B["编码：HEVC / VP9 / AV1<br/>压缩画面 + 打包元数据"]
    B --> C["码流：画面数据 + 元数据<br/>一起传输"]
    C --> D["播放端解码<br/>画面 + 该帧的映射说明"]
    D --> E["显示端按元数据做映射"]
```

这也解释了一个常见困惑：**"我的电视支持 HDR10+，为什么放出来却没有效果？"**——很可能是因为播放链路里某一环（播放器、HDMI、芯片）没能把码流里的元数据完整送达。（见第 15 章）

实体介质与游戏

## 本章小结

- **位深 = 台阶级数**。8bit 256 级、10bit 1024 级、12bit 4096 级；RGB 三通道相乘得到可表达的颜色数。
- **HDR 为什么要 10bit 起步**：PQ 曲线暗部太陡，8bit 会糊出**色带（banding）**；10bit 是为精度，不是为"更艳"。
- **抖动与 FRC** 是用时间上的交替"假装"中间色；**8bit+FRC ≠ 真 10bit**，是"介于两者之间"。
- **色度采样**利用"人眼对亮度敏感、对色度不敏感"：4:4:4 全存、4:2:2 色度水平减半、4:2:0 色度横纵各减半（约省一半数据）。
- **4:2:0 不是画面糊**，它主要影响彩色边缘锐度；影视够用，PC 桌面更爱 4:4:4。
- **RGB vs YCbCr**：YCbCr 把亮度单独拎出来，才方便做色度采样、兼容黑白。
- **ICtCp** 是 HDR 时代更"感知恒定"的编码，常见于 Dolby Vision。
- **编解码** HEVC / VP9 / AV1 负责压缩与承载；HDR 元数据**随码流走**，断了就失效。

## 常见误区与自测

1. **误区：8bit+FRC 就是 10bit。**
   不是。真 10bit 有 1024 级真实台阶；8bit+FRC 原生只有 256 级，靠时间交替"骗"出中间色。日常够用，但暗场、静态渐变下可能露馅。

2. **误区：4:2:0 是画面糊的唯一原因。**
   不是。4:2:0 只减少**色度**信息，主要影响彩色边缘，亮度细节不受影响。画面模糊多半要找分辨率、缩放、带宽降级等原因。

3. **自测：** 为什么 HDR 用 8bit 特别容易出色带，而 SDR 用 8bit 却还好？
   提示：SDR 是相对式、曲线较平缓；**PQ 是绝对式，暗部极陡**，8bit 的台阶在暗部跨度太大。

4. **自测：** 为什么视频普遍采用 YCbCr 而不是 RGB？
   提示：YCbCr 能把**亮度与色度分离**，便于对色度降采样省数据，并天然兼容黑白。
